# Wrap OpenSSL 3.5, then make silent failures loud

mojo_net should get TLS from conda-forge's OpenSSL on the 3.5 long-term-support line (`openssl >=3.5.9,<4`, `libssl.so.3`, supported to 2030-04-08). A new sans-I/O `tls` codec drives it through two memory BIOs and makes no network syscalls of its own. The client comes first, and AWS-LC stays a designed-in second backend until conda-forge carries AWS-LC's LTS branch. The library is not where the exploitable mistakes concentrate. Read advisory by advisory, only 12 of OpenSSL's 121 CVEs since 2020 reached a TLS client or server in default configuration; 10 of them were in certificate parsing, and 7 existed only in the first releases of a new major line. Over the same years, the glue around correct libraries in curl, Python, rust-openssl, Node and Swift NIO kept shipping verification bypasses and use-after-frees. That glue failed mostly because OpenSSL reports success after skipping a check: it verifies nothing by default, takes an empty host name as "check no name", returns `X509_V_OK` when no certificate arrived, counts a missing trust store as loaded, and lets a resumed session inherit an old verdict. So the wrapper must refuse bad inputs before calling OpenSSL and re-check every outcome afterwards. This report turns that into 71 numbered rules, each paired with a test that shows it holds and with a planted bug that proves the test can fail, so a reviewer who is not a TLS expert can check them mechanically. Assurance rests on fifteen pass/fail gates. Most are built on oracles other people wrote (x509-limbo, BetterTLS, real Python and `openssl` peers, AddressSanitizer, sslyze, tlsfuzzer); the rest are fault seams on every OpenSSL call, a daily freshness job and a narrow external review. The milestones run T0 (a 3–5-day linking spike), then T1 (the client codec, 3–4 person-weeks), then H8, P9 and R8 (HTTPS, PostgreSQL and Redis, about 3–4 weeks together), then a review gate, and last T2 and S7 for the server (3–4 weeks). Even done perfectly, the plan leaves library zero-days in certificate parsing, bugs no test imagined, no revocation checking, clock errors and stale root stores; they are stated here, not hidden. Ten decisions remain for the user. The version pin is urgent: the environment resolves OpenSSL 3.6.5 today, and 3.6 stops receiving fixes on 2026-11-01.

## OpenSSL 3.5 LTS is the right base today, and AWS-LC waits for an LTS build

TLS promises three things: nobody can read the traffic, nobody can change it undetected, and the other end is the party the caller meant. Integrations break the third. An encrypted connection to an attacker looks exactly like a working connection, so no test that only checks "it connects" can catch the mistake. Exploitable mistakes enter from three places. The first is a memory-safety bug in the library that a hostile peer can reach. The second is a bug in the glue that drives the library. The third is a configuration that quietly turns a check off. The choice of library controls only the first; the rules in this report control the other two.

**How to read the rules.** Each rule has an identifier a reviewer can cite in a review or a commit message: TL for the library and how it is loaded, TC for client verification, TB for the memory-BIO codec, TS for the server and TA for the supply chain. The test gates are TG1–TG15 and the open decisions TD1–TD10. The two-letter prefixes avoid the repo's milestone names (S7, P9 and so on). Every rule says what the wrapper must do and which test must show it. A rule backed by a source carries its citation; a rule that is design reasoning carries *(inference)*. **One rule governs all the others: every test named here ships with a planted bug that turns it red.** A security test that has never been seen failing proves nothing. This is the repo's existing planted-bug practice, applied to TLS.

### OpenSSL's raw CVE count overstates the risk to this repo

OpenSSL published **121 CVEs from 2020 to 2026-10-26: 14 High, 31 Moderate and 76 Low, with none Critical** ([OpenSSL vulnerabilities](https://openssl-library.org/news/vulnerabilities/index.html)). **63 of them came in 2026 alone**, in a wave driven by AI-assisted discovery: 28 of the 2026 entries credit Aisle Research, Anthropic or Claude ([AISLE](https://aisle.com/blog/aisle-discovers-20-openssl-zero-days-in-6-months)). The research read each advisory against this repo's profile: TLS 1.2 and 1.3 over TCP, memory BIOs, AEAD ciphers and ECDHE, default certificate verification, and no CRL, OCSP or DANE. By that reading, **12 were reachable by a client or server in default configuration and 28 sat behind an opt-in feature. The other 81 were in code a TLS-only user never runs**: CMS, PKCS#7 and #12, CMP, QUIC, DTLS, SM2 and the command-line tools. The split is the researcher's inference from the advisory text. Borderline cases need a second reader, for example CVE-2026-75803, a ChaCha20-Poly1305 tag check skipped through `EVP_Cipher()`.

Two patterns in the twelve shape the plan. **Ten are in X.509 or ASN.1 processing of the peer's certificate chain**, not in the TLS state machine, so certificate parsing is the exposure no configuration removes. And **seven existed only in the first releases of a new major line** (3.0.0–3.0.7 or 4.0.0–4.0.2), which favours an LTS line over the newest major. None of the 121 concerned the memory-BIO code.

### AWS-LC's record is shorter but not directly comparable

AWS-LC lists five advisories ever, all published in March 2026: two `PKCS7_verify` bypasses, an AES-CCM timing issue in the EVP API, a partitioned-CRL scope error, and a name-constraints bypass through the subject-CN fallback. Only the last reaches a TLS client in default configuration, and only through a name-constrained CA ([AWS-LC advisories](https://github.com/aws/aws-lc/security/advisories)).

The comparison with OpenSSL is not like for like. AWS-LC's policy does not count invalid caller arguments or documented-but-unsafe compatibility APIs as vulnerabilities ([AWS-LC SECURITY.md](https://github.com/aws/aws-lc/blob/main/SECURITY.md)), and the BoringSSL code it descends from never issued advisories. At least three of the five bugs were in OpenSSL-compatibility code added after the fork, from v1.41 and v1.61, so AWS-LC's attack surface is growing toward OpenSSL's. Among the remaining candidates, wolfSSL had 79 NVD CVEs in 2026 and is GPLv3 ([NVD](https://services.nvd.nist.gov/rest/json/cves/2.0?virtualMatchString=cpe:2.3:a:wolfssl:wolfssl)). GnuTLS and Mbed TLS show small but steady streams of High-rated issues, and LibreSSL's low count comes with no conda-forge package.

### AWS-LC has the stronger proofs, OpenSSL the wider scrutiny

AWS-LC's CI checks formal proofs on every change. HOL Light proofs cover its P-256, P-384, P-521, X25519 and Ed25519 assembly on both x86_64 and aarch64, and SAW proofs cover AES-256-GCM and SHA-384/512 on particular Intel CPUs ([AWS-LC README](https://github.com/aws/aws-lc/blob/main/README.md)). Those proofs remove the carry-propagation and constant-time bugs of hand-written assembly, the class behind CVE-2022-2274. But they cover primitives, not the X.509 code where OpenSSL's reachable bugs actually were.

OpenSSL has wider scrutiny instead. It has continuous OSS-Fuzz coverage, in which AWS-LC is not enrolled ([OSS-Fuzz projects](https://github.com/google/oss-fuzz/tree/master/projects)), and a 2023 OSTIF/Trail of Bits audit of OpenSSL 3: 9 engineer-weeks, 23 findings, no CVEs ([OSTIF](https://ostif.org/openssl-audit-complete/)). It also went through the 2025–2026 AI sweeps, and that they found so little reachable from TLS is itself evidence about the TLS and X.509 code. The research found no public third-party audit of AWS-LC. FIPS decides nothing here, because conda-forge builds OpenSSL with `no-fips` ([openssl-feedstock build.sh](https://github.com/conda-forge/openssl-feedstock/blob/main/recipe/build.sh)).

### Maintenance and packaging settle the choice

The OpenSSL support windows ([release strategy](https://openssl-library.org/policies/releasestrat/)):

| Line | Supported until | Note |
|---|---|---|
| 3.5 (LTS) | 2030-04-08 | ABI guaranteed within the major version |
| 3.6 | **2026-11-01** | what the repo's environment resolves today, through Python |
| 4.0 | 2027-05-14 | not LTS; new soname `libssl.so.4` |
| 4.2 (next LTS) | due April 2027 | |

conda-forge pins `openssl: '3.5'` globally, and its Python requires `openssl >=3.5.9,<4.0a0` ([conda-forge pinning](https://github.com/conda-forge/conda-forge-pinning-feedstock/blob/main/recipe/conda_build_config.yaml)), so a 4.x dependency would make the repo's environment unsolvable today. conda-forge shipped every 2025–2026 OpenSSL security release within 0–5 days, 3.5.9 included ([openssl-feedstock 3.5.x](https://github.com/conda-forge/openssl-feedstock/commits/3.5.x)).

AWS-LC fits worse for now. Its mainline releases every one to three weeks and promises no ABI stability. The ABI promise exists only on its LTS branch, 4.x, cut 2025-09-12 and supported to about September 2030 ([VERSIONING.md](https://github.com/aws/aws-lc/blob/main/VERSIONING.md)). conda-forge packages mainline only, from a feedstock created on 2026-10-06 that pins each minor version and has no security-response record yet ([aws-lc-feedstock](https://github.com/conda-forge/aws-lc-feedstock/blob/main/recipe/recipe.yaml)). AWS-LC's packaging advantage is real, though: `libssl-awslc` installs beside OpenSSL without conflict.

The notes disagree on one point. The assurance research suggested pinning `>=3.6.5,<3.7`, but 3.6 leaves support in six days, so that pin would cut the repo off from fixes almost at once. The library research's 3.5 recommendation stands.

### The other candidates fail a hard constraint

BoringSSL promises no API or ABI stability and has no conda-forge package ([BoringSSL README](https://boringssl.googlesource.com/boringssl/+/HEAD/README.md)). s2n-tls and rustls-ffi drive I/O through callbacks into the host language, which the repo's Mojo pitfalls make the riskiest FFI shape. rustls-ffi also has no ABI guarantee and no conda-forge package ([rustls-ffi](https://github.com/rustls/rustls-ffi)). Mbed TLS 4 has just broken its API, and wolfSSL is GPLv3.

### Attack surface has to be cut at run time

The project cannot rebuild conda-forge's binary, which ships the legacy provider and kTLS support compiled in (`enable-legacy no-fips no-module no-zlib shared threads`, plus `enable-ktls` on Linux). The reduction therefore has to happen at run time, which the rules below do. Most of the 28 opt-in CVEs disappear when the wrapper never enables CRL, OCSP, DANE, raw public keys, certificate policies or legacy key exchange. Three opt-in CVEs were triggered by *hardening* options: `SSL_OP_NO_TICKET` used on its own, `X509_V_FLAG_X509_STRICT` in 1.1.1, and the `DEFAULT` group keyword. That is why the rules prescribe exact option sets rather than "more is safer".

| Rule | The wrapper must | A test or check must show |
|---|---|---|
| **TL1** | Declare `openssl >=3.5.9,<4` and `ca-certificates` as run dependencies of the `tls` package and the recipe, and pin the development environment to `openssl 3.5.*` now, instead of inheriting 3.6 from Python ([release strategy](https://openssl-library.org/policies/releasestrat/)). | A CI step calls `OpenSSL_version()` from a test and fails unless it reports 3.5.x on both architectures. |
| **TL2** | Bind only symbols whose ELF version node is `OPENSSL_3.5.0` or older, so the package loads on any 3.5-or-later 3.x library *(inference)*. | A readelf check, run like `api-check`, fails if the binding table names a symbol from a later node such as `OPENSSL_3.6.0`. |
| **TL3** | Refuse at load to run on anything older than 3.5 in the 3.x line, and log the loaded version and `OPENSSLDIR`, because defaults such as the trust-store path depend on the install prefix ([AWS-LC ssl.h](https://github.com/aws/aws-lc/blob/main/include/openssl/ssl.h)) *(the 3.5 floor is an inference)*. | A fault seam that reports version 3.4 makes context creation fail with a clear error. |
| **TL4** | Call `OPENSSL_init_ssl` with `OPENSSL_INIT_NO_LOAD_CONFIG` before any other OpenSSL call, and build every context with `SSL_CTX_new_ex` in a private `OSSL_LIB_CTX` that loads only the default provider ([OPENSSL_init_crypto](https://docs.openssl.org/3.5/man3/OPENSSL_init_crypto/); [SSL_CTX_new](https://docs.openssl.org/3.5/man3/SSL_CTX_new/)). | With `OPENSSL_CONF` pointing at a hostile file (TLS 1.0 floor, RSA key exchange), the version and cipher negative tests still fail closed, and `OSSL_PROVIDER_available` finds no legacy provider in the private context. Whether this blocks every injection route is unverified; T0 must check it. |
| **TL5** | Never call `SSL_set_SSL_CTX` (CVE-2026-72897), `SSL_select_next_proto` (CVE-2024-5535), `SSL_free_buffers` (CVE-2024-4741) or `SSL_check_chain` (CVE-2020-1967). Nor any NPN, early-data, PSK, SRP, keylog, password-callback, OCSP, DANE or raw-public-key API, nor any CRL or policy verification flag ([OpenSSL vulnerabilities](https://openssl-library.org/news/vulnerabilities/index.html)). | The binding table is an allowlist, and a CI grep over `src/tls` fails on any name on this list. |
| **TL6** | Never bind an I/O BIO or fd setter (`BIO_s_socket`, `BIO_new_socket`, `BIO_s_connect`, `BIO_s_accept`, `BIO_new_fd`, or `SSL_set_fd` and its read and write variants), and never set `SSL_OP_ENABLE_KTLS`; libssl talks only to memory BIOs. | The allowlist check, plus a codec-only test run under `strace` (or a seccomp filter) that shows no socket syscall. *(Inference: `nolibc-check` inspects only the binary's own imports, so it cannot see what libssl calls.)* |
| **TL7** | Confine `external_call` and `OwnedDLHandle` to `src/tls/ffi*.mojo`, and record the exception in `docs/design.md`: libssl and libcrypto may make their own memory, randomness and build-time file-read syscalls, and never socket, poll or epoll ones. | `import-check` fails on an FFI call anywhere else in `src/`. |
| **TL8** | Run every OpenSSL call for a connection on the OS thread that owns it, build each `SSL_CTX` once and treat it as read-only after the first `SSL_new`, and never call OpenSSL from the Mojo runtime's worker threads ([openssl-threads(7)](https://github.com/openssl/openssl/blob/master/doc/man7/openssl-threads.pod)). | A built context exposes no setters (API review), and a ThreadSanitizer run is required before any context is shared across threads. |

## A client must re-check five outcomes, because OpenSSL reports success when it skipped them

**The danger for a client is a connection that works.** Suppose the wrapper skips the identity check. The handshake completes and data flows encrypted, and nothing visible fails: the attacker in the middle simply holds a valid certificate for some other name, which anyone can obtain for a domain they control. The 2012 study titled "The Most Dangerous Code in the World" found certificate validation "completely broken in many security-critical applications and libraries". It blamed "badly designed APIs of SSL implementations (such as JSSE, OpenSSL, and GnuTLS)" ([Georgiev et al., CCS 2012](https://www.cs.cornell.edu/~shmat/shmat_ccs12.pdf)). Those APIs have not changed. Each row below is a way OpenSSL or AWS-LC reports success after a check did not happen.

| Silent failure | What actually happens | Source |
|---|---|---|
| Default verify mode | Both libraries default to `SSL_VERIFY_NONE`: the handshake "will be continued regardless of the verification result" | [SSL_CTX_set_verify(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_CTX_set_verify.pod) |
| Empty host name | `SSL_set1_host("")` or `X509_VERIFY_PARAM_set1_host` with an empty name clears the name list and returns 1; a length of 0 means "call `strlen`" | [SSL_set1_host(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_set1_host.pod); [x509_vpm.c](https://github.com/openssl/openssl/blob/openssl-3.5/crypto/x509/x509_vpm.c) |
| No certificate at all | `SSL_get_verify_result` "can still be X509_V_OK" when the peer presented no certificate | [SSL_get_verify_result(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_get_verify_result.pod) |
| No trust store | `SSL_CTX_set_default_verify_paths`: "A missing default location is still treated as a success" | [SSL_CTX_load_verify_locations(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_CTX_load_verify_locations.pod) |
| Permissive callback | A verify callback that returns 1 lets every failed chain through | [SSL_CTX_set_verify(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_CTX_set_verify.pod) |
| Resumed session | `SSL_set_session` copies the stored `verify_result` into the new connection | [ssl_sess.c](https://github.com/openssl/openssl/blob/openssl-3.5/ssl/ssl_sess.c) |
| Subject CN fallback | OpenSSL 3.5 matches the subject CN when no SAN is present; AWS-LC checks the CN by default, the path of its March 2026 bypass | [X509_check_host(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/X509_check_host.pod); [GHSA-3jrg-j22w-mpmc](https://github.com/aws/aws-lc/security/advisories/GHSA-3jrg-j22w-mpmc) |

The same shapes keep reappearing in mature integrations. curl's mbedTLS glue skipped the certificate check entirely for hosts given as IP addresses ([CVE-2024-2466](https://curl.se/docs/CVE-2024-2466.html)). rust-openssl's `set_host("")` cleared the name list ([RUSTSEC-2023-0044](https://rustsec.org/advisories/RUSTSEC-2023-0044.html)). LibreSSL handled a zero length differently, which silently skipped Python's host check ([CVE-2018-8970](https://www.python.org/pipermail/python-dev/2018-April/152632.html)). And in September 2026, curl fixed a pinning check that was skipped on connections where no certificate was presented ([CVE-2026-80230](https://curl.se/docs/CVE-2026-80230.html)). The rules therefore follow one pattern: refuse bad inputs before the call, check every return value, and confirm the outcome independently after the handshake.

### Trust anchors are loaded explicitly and counted (TC1–TC3)

Which roots a process trusts depends on which libssl it loaded. On this host, conda-forge's OpenSSL looks in `$CONDA_PREFIX/ssl`, where `ca-certificates` provides a `cacert.pem` of 120 certificates, while Debian's looks in `/usr/lib/ssl` (both observed). AWS-LC tells callers not to rely on default paths at all ([AWS-LC ssl.h](https://github.com/aws/aws-lc/blob/main/include/openssl/ssl.h)). With `SSL_VERIFY_PEER` set, an empty store still fails closed, but only at handshake time and with an opaque "unable to get local issuer" error. The wrapper should fail earlier, when the context is built, with a message that names the file.

Python 3.13 and curl now enable `X509_V_FLAG_PARTIAL_CHAIN` by default ([CPython ssl.py](https://github.com/python/cpython/blob/main/Lib/ssl.py); [curl openssl.c](https://github.com/curl/curl/blob/master/lib/vtls/openssl.c)). This plan does not, because the flag turns any intermediate or leaf that slips into a CA file into a full trust anchor. It is a judgement call, and failing closed is the safer direction.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC1** | Build the trust store explicitly, in this order: the caller's CA bundle if given; else exactly `SSL_CERT_FILE` (missing, unparsable or empty is an error, with no fallback); else `SSL_CERT_DIR`, which must exist and be non-empty since a directory store loads lazily and cannot be counted *(inference)*; else the loaded library's `X509_get_default_cert_file()`; else the first existing file in Go's distribution list ([root_linux.go](https://github.com/golang/go/blob/master/src/crypto/x509/root_linux.go)). Load the file with `SSL_CTX_load_verify_locations` and check its return value. Never rely on `SSL_CTX_set_default_verify_paths`, and refuse to build a context that holds zero anchors. | `SSL_CERT_FILE=/nonexistent` and an empty bundle each fail at context build, with the path in the error. A one-certificate bundle works. With `SSL_CERT_FILE` set, the system roots are never consulted. |
| **TC2** | Offer exactly two trust choices: system roots, or "these CA certificates" (a PEM file or bytes). The second replaces the first and never adds to it. Offer no "accept self-signed" switch (a self-signed leaf is trusted by listing it, since it is its own root), and leave `X509_V_FLAG_PARTIAL_CHAIN` off ([NIST SP 800-52r2 §4.5.2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-52r2.pdf)). | A bundle holding only an intermediate fails to verify. A client given a custom CA fails against a host signed by a public root. Listing a self-signed leaf works. |
| **TC3** | Set `X509_V_FLAG_X509_STRICT` on OpenSSL (Python 3.13 does, and AWS-LC forces it), keep `X509_V_FLAG_TRUSTED_FIRST`, and never change the default purpose, trust setting or depth limit (100). libssl sets the purpose itself, and CVE-2021-3450 hit only applications that overrode it ([advisory 2021-03-25](https://openssl-library.org/news/secadv/20210325.txt)). | A leaf whose EKU allows only client authentication, an expired leaf and a not-yet-valid leaf each fail. |

### Host names are refused, classified and normalized before OpenSSL sees them (TC4–TC7)

RFC 9525, which replaced RFC 6125 in 2023, sets the rules for matching a name against a certificate. The Common Name "MUST NOT be used to identify a service". A wildcard must be the whole left-most label, and it matches exactly one label. IP identities compare octet for octet. The RFC also warns that "a textual representation of an IPv4 address might be misinterpreted as a valid FQDN" ([RFC 9525](https://www.rfc-editor.org/rfc/rfc9525)). RFC 6066 adds that SNI carries no IP literal and no trailing dot ([RFC 6066](https://www.rfc-editor.org/rfc/rfc6066)).

OpenSSL's matcher is looser by default. It accepts partial wildcards such as `w*.example.com`, falls back to the CN when no SAN is present, takes a leading dot as a request for sub-domain matching, and compares trailing dots exactly ([X509_check_host(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/X509_check_host.pod); [v3_utl.c](https://github.com/openssl/openssl/blob/openssl-3.5/crypto/x509/v3_utl.c)). CPython, Go and rust-openssl all classify the target before configuring OpenSSL, and CPython and Go refuse empty names ([CPython _ssl.c](https://github.com/python/cpython/blob/main/Modules/_ssl.c); [Go handshake_client.go](https://github.com/golang/go/blob/master/src/crypto/tls/handshake_client.go)). The rules below take the strictest of their choices on each point.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC4** | Refuse with `InvalidInput`, before any OpenSSL call: an empty host; any NUL, control or non-ASCII byte (A-labels only); a leading dot; a `*`; an empty label; a label over 63 or a name over 253 bytes *(inference from DNS limits)*; an IPv6 zone ID; and any numeric-looking name that is not a strict IP literal, such as `127.1`, `0x7f.0.0.1` or `010.0.0.1`. Decide IP versus DNS once, with the repo's strict `net.addr` parser, never with OpenSSL's ([RFC 9525 §7.4](https://www.rfc-editor.org/rfc/rfc9525)). | Each refused spelling raises `InvalidInput`, and the peer receives no byte. |
| **TC5** | For a DNS target: lower-case the name and strip exactly one trailing dot. Then `SSL_set_tlsext_host_name` (on OpenSSL, `SSL_ctrl(ssl, 55, 0, name)`) must return 1, and so must `X509_VERIFY_PARAM_set1_host(SSL_get0_param(ssl), name, len)`, with `len > 0` passed explicitly. For an IP target: send no SNI, and `X509_VERIFY_PARAM_set1_ip(param, bytes, 4 or 16)` must return 1. Use these `X509_VERIFY_PARAM` calls rather than `SSL_set1_host`, which 4.0 deprecates and whose IP handling the 3.0–3.3 docs do not describe ([SSL_set1_host(3), 4.0](https://github.com/openssl/openssl/blob/openssl-4.0/doc/man3/SSL_set1_host.pod)). | Dialing `127.0.0.1` fails against a certificate with only a DNS SAN, and against an IP SAN of `127.0.0.2`. With an IP SAN of `127.0.0.1` it passes, and the peer sees no SNI. `localhost.` passes and sends SNI `localhost`. `::1` behaves like `127.0.0.1`. |
| **TC6** | Set the host flags `X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS` and `X509_CHECK_FLAG_NEVER_CHECK_SUBJECT`: RFC 9525's rule, Go's behaviour since 1.15, and AWS-LC's own advice ([AWS-LC ssl.h](https://github.com/aws/aws-lc/blob/main/include/openssl/ssl.h)). | A CN-only certificate fails, and so does `w*.example.test`. `*.example.test` matches `a.example.test`, but neither `a.b.example.test` nor `example.test`. A SAN with an embedded NUL fails (the null-prefix attack, CVE-2009-2408). |
| **TC7** | Accept an optional expected identity (`server_name`) that is separate from the dial address, as Go's `ServerName` is. It is never empty, never derived from bytes the server sent, and validated like TC4. | Dialing `127.0.0.1` with `server_name` set to `localhost` passes against a DNS SAN of `localhost`. An empty override is refused. No API path sets the identity from received data. |

### The connection counts only after a six-part gate (TC8–TC10)

`X509_V_OK` can mean "nothing was checked", so the wrapper decides for itself when a connection is established. Each condition below closes a different silent path from the table above, and their redundancy is deliberate.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC8** | Call `SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL)`: exactly that bit, and no callback. Expose no setter for the verify mode, callback, host flags or partial chains, and read no environment variable that disables verification ([SSL_CTX_set_verify(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_CTX_set_verify.pod)). | A planted bug that sets `SSL_VERIFY_NONE` turns the untrusted-root, wrong-host and expired cases red. |
| **TC9** | Treat the connection as established only when all six hold: `SSL_do_handshake` returned 1; `SSL_get0_peer_certificate` is non-NULL; `SSL_get_verify_result` equals `X509_V_OK`; an independent `X509_check_host` (DNS) or `X509_check_ip` (IP) on the peer leaf, with the same flags, returns exactly 1, and for DNS targets on OpenSSL `SSL_get0_peername` is non-NULL as well; `SSL_version` is at least `0x0303`; and the ALPN result is acceptable (TC15). *(Inference: OpenSSL records a matched peer name only for host-name matches, so `SSL_get0_peername` is no signal for IP targets; T0 confirms.)* | A fault seam that forces each condition false in turn makes the connection fail with the right category. A seam reporting "verify OK, no certificate" fails. |
| **TC10** | Pass no plaintext to `SSL_write_ex` and emit no data event before the gate passes, and free the `SSL` object as soon as the gate fails. | Against a wrong-host certificate, the Python peer logs zero application bytes received. A peer that sends bytes and closes before the handshake gets an error, never data: the shape of Python's [CVE-2023-40217](https://nvd.nist.gov/vuln/detail/CVE-2023-40217). |

### Policy fixes a TLS 1.2 floor and refuses everything legacy (TC11–TC13)

The two libraries differ exactly where a wrapper's defaults matter. AWS-LC's built-in version floor is TLS 1.0, according to a pull-request description rather than the code ([aws-lc #3503](https://github.com/aws/aws-lc/pull/3503)), and its security-level calls are no-ops. OpenSSL's default security level of 2 can be lowered at build time ([SSL_CTX_set_security_level(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_CTX_set_security_level.pod)). The options word is a `uint64_t` in OpenSSL 3 and a `uint32_t` in AWS-LC, and a wrong width in an FFI declaration is a silent ABI bug.

Both libraries already offer the post-quantum hybrid X25519MLKEM768 as a default key share. Mozilla's 6.0 intermediate profile lists TLS 1.2 and 1.3, six ECDHE AEAD suites for TLS 1.2, and the groups X25519MLKEM768, X25519, P-256 and P-384 ([Mozilla guidelines 6.0](https://ssl-config.mozilla.org/guidelines/6.0.json)). NIST says TLS 1.3 clients "should not send 0-RTT data" ([NIST SP 800-52r2 §4.6](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-52r2.pdf)).

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC11** | Set the minimum version to TLS 1.2 explicitly: `SSL_CTX_ctrl(ctx, 123, 0x0303, NULL)` on OpenSSL, or the real function with a `uint16_t` on AWS-LC. Assert that the call returns 1 and that the constant is non-zero, since 0 means "library default". Leave the maximum at the default, and never retry with a lower floor after a failure. | A peer limited to TLS 1.1 is refused. No failure leads to a second dial with weaker settings (a seam counts dials). |
| **TC12** | On OpenSSL, call `SSL_CTX_set_security_level(ctx, 2)` explicitly. Restrict TLS 1.2 to Mozilla intermediate's six ECDHE AEAD suites and check the return value; AWS-LC uses `SSL_CTX_set_strict_cipher_list`. Keep the TLS 1.3 suites at their defaults. Use the library's default groups, or exactly `X25519MLKEM768:X25519:P-256:P-384`, never with the `DEFAULT` keyword (CVE-2026-2673). Never silently retry without the post-quantum group. | A peer offering only RSA key exchange or CBC suites fails. A server with an RSA-1024 certificate fails. |
| **TC13** | Add `SSL_OP_NO_COMPRESSION` and `SSL_OP_NO_RENEGOTIATION`. Never set `SSL_OP_LEGACY_SERVER_CONNECT`, `SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION` or `SSL_OP_IGNORE_UNEXPECTED_EOF`. Send no early data, and enable no PSK, SRP or anonymous suites ([SSL_CTX_set_options(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CTX_set_options.pod)). | `SSL_CTX_get_options` returns exactly the expected bit set. An `openssl s_server` renegotiation request (the `R` command, TLS 1.2) never produces a second handshake. |

### Revocation is absent by design, and the documentation must say so (TC14)

A revoked certificate is one its CA has withdrawn, typically because the key leaked. Checking for revocation sounds mandatory, and NIST says a client "shall perform revocation checking" ([NIST SP 800-52r2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-52r2.pdf)). Practice has moved away from it. Go's verifier "doesn't do any revocation checking" ([Go verify.go](https://github.com/golang/go/blob/master/src/crypto/x509/verify.go)). Python and OpenSSL check no CRLs by default, and curl's OCSP-stapling check is off by default. Let's Encrypt turned its OCSP responders off on 2025-08-06 ([Let's Encrypt](https://letsencrypt.org/2024/12/05/ending-ocsp/)). Browsers now push compressed revocation sets instead: Firefox has used CRLite since version 137, while Chrome's hand-picked CRLSets cover about 35,000 of four million revocations ([Mozilla Hacks](https://hacks.mozilla.org/2025/08/crlite-fast-private-and-comprehensive-certificate-revocation-checking-in-firefox/)).

Revocation code is also a bug source: CVE-2026-35188 was a double free when a client checks a stapled OCSP response. What actually bounds the exposure is the shrinking certificate lifetime: 200 days from 2026-03-15, 100 days from 2027-03-15 and 47 days from 2029-03-15 ([CA/B Forum SC-081v3](https://cabforum.org/2025/04/11/ballot-sc081v3-introduce-schedule-of-reducing-validity-and-data-reuse-periods/)).

| Rule | The wrapper must | A test or check must show |
|---|---|---|
| **TC14** | Do no online OCSP, CRL or AIA fetching inside `tls`, and say so in `docs/tls.md` as a deliberate departure from NIST. A later, opt-in CRL-file mode for private PKIs must fail hard, with `X509_V_FLAG_CRL_CHECK` and `X509_V_FLAG_CRL_CHECK_ALL`: a missing or expired CRL is an error, unlike libpq's silent skip. It must never combine with partial chains. | The documentation states the stance. When CRL mode lands, a missing CRL and an expired CRL each fail the handshake. |

### ALPN, resumption and pooling are where the reuse bugs live (TC15–TC17)

ALPN is how client and server agree on the protocol inside TLS, such as "http/1.1" or "postgresql". Its API has two traps. `SSL_CTX_set_alpn_protos` returns **0 on success**, the reverse of almost every other OpenSSL call ([SSL_CTX_set_alpn_select_cb(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CTX_set_alpn_select_cb.pod)). And the helper `SSL_select_next_proto` could leak up to 255 bytes of memory when given an empty list ([CVE-2024-5535](https://openssl-library.org/news/secadv/20240627.txt)).

Session resumption skips most of a handshake by reusing an earlier session, and its risk is concrete. OpenSSL copies the stored verdict into the resumed connection, and curl once resumed a proxy's TLS 1.3 ticket as if it came from the origin server, bypassing the origin's certificate check ([CVE-2021-22890](https://curl.se/docs/CVE-2021-22890.html)). Connection pools have the same failure in another form: curl reused connections across different TLS settings more than once ([curl advisories](https://curl.se/docs/security.html)).

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC15** | Offer ALPN only as a non-empty wire-format list (`\x08http/1.1`, or `\x0apostgresql` for direct PostgreSQL), through one helper that treats a non-zero return as failure. Never call `SSL_select_next_proto` or any NPN API. After the handshake, HTTP accepts no protocol or exactly `http/1.1`, direct PostgreSQL requires exactly `postgresql`, and anything else is `InvalidData` ([libpq fe-secure-openssl.c](https://github.com/postgres/postgres/blob/master/src/interfaces/libpq/fe-secure-openssl.c)). | A unit test of the helper's inverted return value. A seam that makes `SSL_get0_alpn_selected` return `h2` gives `InvalidData`. Direct PostgreSQL against a server without ALPN is refused. |
| **TC16** | Do no client session resumption in v1: never call `SSL_set_session`, install no new-session callback, and keep client-side caching off (it is off by default). If resumption is added later, the cache key must hold the normalized identity and port, the SNI, the ALPN offer, the trust-store generation, the verify flags, the client-certificate identity, any proxy identity and the `SSL_CTX` instance. Only sessions that passed TC9 may be stored, and the TC9 gate and the leaf's `notAfter` are re-checked on every resumption, as Go does ([Go handshake_client.go](https://github.com/golang/go/blob/master/src/crypto/tls/handshake_client.go)). | No connection in the suite resumes (`SSL_session_reused` returns 0), even on a second dial to the same server. |
| **TC17** | Key every connection pool (`http.client`, `pg.Pool`) by every TLS setting: trust-store identity, expected identity, SNI, ALPN offer, client-certificate identity and verify flags *(inference from curl's reuse CVEs)*. | Two requests to the same host and port with different CA settings use two connections. |

### Failures name their reason and never offer a way to continue (TC18)

CPython reports the verify code and gives specific messages for host and IP mismatches ([CPython _ssl.c](https://github.com/python/cpython/blob/main/Modules/_ssl.c)). Georgiev's advice to library authors was to "not silently skip important functionality such as hostname verification", but to raise an error ([Georgiev et al.](https://www.cs.cornell.edu/~shmat/shmat_ccs12.pdf)). Diagnostics hide one more trap. Swift NIO SSL read the `ASN1_STRING` member of BoringSSL's `GENERAL_NAME` union for every SAN entry without checking the entry's type. For other name types the union holds a different structure, so the code read a pointer and a length out of unrelated memory: a critical out-of-bounds read ([CVE-2026-43820](https://github.com/apple/swift-nio-ssl/security/advisories)).

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC18** | Raise one error for "peer failed authentication". It carries a category (untrusted chain, expired or not yet valid, host mismatch, IP mismatch, no peer certificate, weak key, no trust store, protocol version, ALPN mismatch, server refused TLS), the `X509_V_ERR_*` code and its text, the normalized expected identity and the drained error queue. Omit the failing depth, which would need a verify callback. Include no peer-certificate fields in v1, and read C structures only through accessor functions, never as mirrored structs or unions. On any failure, `SSL_free` and close; no API keeps a connection whose verification failed. | Each negative case asserts its category. An API review confirms that nothing builds a stream from a failed handshake. |

### PostgreSQL needs exactly one byte before TLS, and only verify-full authenticates (TC19–TC21)

PostgreSQL starts TLS in-band. The client sends an `SSLRequest` (the code 80877103), and the server answers with a single byte: `S` to start TLS, `N` to refuse. Two attacks live in that exchange ([PostgreSQL protocol flow](https://www.postgresql.org/docs/current/protocol-flow.html)).

The first is buffer-stuffing. A man in the middle appends bytes after the `S`, and a client that reads more than one byte treats them as decrypted data once TLS starts. The attacker can then "inject false responses to the client's first few queries, despite the use of SSL certificate verification and encryption" ([CVE-2021-23222](https://www.postgresql.org/support/security/CVE-2021-23222/)). The second is unauthenticated error text: an error the server sends before TLS must not be shown to the user, "since the server has not been authenticated" (CVE-2024-10977).

libpq's modes are a trap of their own ([libpq-ssl](https://www.postgresql.org/docs/current/libpq-ssl.html)). `disable`, `allow` and `prefer` give no protection against a man in the middle, and the default, `prefer`, is one the manual says "makes no sense from a security point of view". `require` encrypts without authenticating the server, and `verify-ca` protects only as far as "CA policy" does. Only `verify-full` checks both the chain and the host name.

Two newer features help. `sslrootcert=system` forces `verify-full` and makes weaker modes an error, since "it is trivial for anyone to obtain a certificate trusted by the system for a hostname they control". Direct TLS (`sslnegotiation=direct`, PostgreSQL 17) skips the `SSLRequest` but requires ALPN `postgresql` ([libpq-connect](https://www.postgresql.org/docs/current/libpq-connect.html)). Today `pg` refuses every TLS setting as `Unsupported` (`docs/pg.md`); P9 replaces that refusal with the rules below.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC19** | Send the `SSLRequest`, then read exactly one byte from the socket, bypassing the buffered reader. On `S`, start TLS, and treat any further byte already received as `InvalidData` (CVE-2021-23222). `N` is an error under any verifying mode. `E` or any other byte closes the connection with "server refused TLS", and the server's text is never shown (CVE-2024-10977). | The `pg_oracle.py` peer answers `S` plus extra bytes in one segment: the result is `InvalidData`, and none of those bytes reach OpenSSL. An `E` with an ErrorMessage surfaces none of its text. |
| **TC20** | Accept `disable` (explicit plaintext), `verify-full` (the default whenever TLS is requested), `verify-ca` only with an explicit `sslrootcert` file, and `sslrootcert=system` with libpq's meaning. Refuse `allow` and `prefer`, which are downgradable by construction. Give `require` the semantics chosen in TD4; the recommendation is to enforce `verify-full`. Never reproduce "encrypt without authenticating". | `Config.parse` tests: requesting TLS means verify-full; `prefer` and `allow` give `InvalidInput`; there is no silent plaintext fallback; `require` behaves as decided. |
| **TC21** | For direct TLS, offer ALPN `postgresql` and require it selected. Send cancel requests over TLS, verified against the same expected host name, not just the session's peer IP. Refuse a TLS-requiring mode combined with a Unix-socket host, instead of silently ignoring it as libpq does *(inference, following the repo's "refused, not ignored" rule)*. | A `pg_cluster.py` server with `ssl=on` and a trustme certificate: verify-full passes, a wrong host fails, and a cancel over TLS to a wrong-name server fails. |

### Redis and Valkey start TLS at the first byte and usually demand a client certificate (TC22)

Valkey serves TLS on a separate port and, by default, requires clients to present a valid certificate (`tls-auth-clients`) ([valkey.conf](https://github.com/valkey-io/valkey/blob/unstable/valkey.conf)). Clusters report IP addresses in redirects unless they announce hostnames, which is the usual pressure on clients to switch host checks off. redis-py even accepts `ssl_cert_reqs` from the URL, so a connection string can disable verification ([redis-py connection.py](https://github.com/redis/redis-py/blob/master/redis/connection.py)).

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TC22** | Run `rediss://` as TLS from the first byte, with TC1–TC18 unchanged. Load a client certificate and key with `SSL_CTX_use_certificate_chain_file`, then `SSL_CTX_use_PrivateKey_file`, then `SSL_CTX_check_private_key`. Verify redirected IPs against IP SANs or the explicit `server_name` (TC7), never against a name the server supplies, and refuse any URL parameter that would weaken verification. | A `valkey_server.py` instance with `tls-port` and `tls-auth-clients yes`: the server refuses a client without a certificate, a wrong CA fails, the right pair passes, and `?ssl_cert_reqs=none` is `InvalidInput`. |

### HTTPS treats every new host as a new verification (TC23)

| Rule | The wrapper must | A test must show |
|---|---|---|

When proxies arrive, the origin's identity and SNI apply inside CONNECT, an HTTPS proxy has its own identity and cache key (CVE-2021-22890), and proxy environment variables never change origin verification. | A redirect to a host whose certificate is wrong fails. ## The codec owns every buffer it lends to C and latches every failure

Behind memory BIOs, OpenSSL is a black box with two in-memory pipes. The codec writes the ciphertext the socket received into the read pipe, asks OpenSSL to make progress, reads back whatever OpenSSL wants sent, and interprets one of thirteen result codes. Nothing in that loop touches the network, which is how the repo's own sockets and epoll keep every network syscall.

The loop can go wrong in eight ways, and each has bitten a mature wrapper. The codec can free memory that C still uses, misread a result code, or trust a stale thread-local error. It can forget that a read can produce output, or change a buffer between a write and its retry. And it can mistake a cut connection for a clean close, call a macro as if it were a function, or let a peer grow memory without bound.

The first is the most dangerous for this repo. Node's TLS layer had a CVSS 8.1 use-after-free ([CVE-2020-8265](https://security-tracker.debian.org/tracker/CVE-2020-8265)). rust-openssl freed a temporary C string before the call that used it ([RUSTSEC-2025-0022](https://rustsec.org/advisories/RUSTSEC-2025-0022.html)). curl passed OpenSSL a library context it held no reference to ([CVE-2026-80229](https://curl.se/docs/CVE-2026-80229.html)). Mojo's destroy-after-last-use rule makes this class likely: an owner whose last Mojo use comes before the C call that dereferences it is already gone.

The codec fits contract 1 (`docs/design.md`) directly:

| Contract 1 | What the TLS client codec does |
|---|---|
| `feed(bytes)`, at most `feed_capacity()` | `ERR_clear_error()`, then `BIO_write_ex` copies the bytes into the read BIO. Then it pumps: `SSL_do_handshake` while handshaking, otherwise `SSL_read_ex` in a loop until `WANT_READ`, draining the write BIO after every call. |
| `feed_eof()` | After every received byte has been fed, `BIO_set_mem_eof_return(rbio, 0)` (on OpenSSL, `BIO_ctrl(rbio, 130, 0, NULL)`), then one more pump. |
| `next_event()` | Small events: `Established` (version, ALPN), `Data`, `PeerClosed`, `Truncated`, `Failed`. Or a `poll(mut ev)` that refills a reused event, as `pg` and `redis` do, to avoid Mojo 1.2's slow `Optional` of a large struct. |
| `poll_transmit(out)` | Appends the drained ciphertext: handshake messages, records, alerts, KeyUpdate replies. |
| `write(plaintext)` (TLS-specific) | Copies into a codec-owned queue, passed to `SSL_write_ex` only after the TC9 gate. |
| `next_deadline()` / `handle_timeout` | An absolute handshake deadline, for drivers that want one (TS8) *(inference)*. |

The result code from `SSL_get_error` decides everything, and the two libraries do not agree on its numbering ([ssl.h.in](https://github.com/openssl/openssl/blob/master/include/openssl/ssl.h.in); [AWS-LC ssl.h](https://github.com/aws/aws-lc/blob/main/include/openssl/ssl.h)):

| Value | OpenSSL 3.5 meaning | AWS-LC meaning | Codec action |
|---|---|---|---|
| 0 `NONE` | success | same | progress |
| 2 `WANT_READ` | needs more ciphertext | same | wait for input |
| 3 `WANT_WRITE` | cannot occur with a memory write BIO *(inference: its writes always succeed)* | same | drain and retry at most twice, then `Failed` |
| 6 `ZERO_RETURN` | peer sent close_notify | same | `PeerClosed` |
| 1 `SSL`, 5 `SYSCALL` | fatal; never call `SSL_shutdown` | same; AWS-LC also reports an EOF as `SYSCALL` with return 0 | `Failed`, or `Truncated` if EOF was fed |
| 9, 11, 12 | `WANT_ASYNC`, `WANT_CLIENT_HELLO_CB`, `WANT_RETRY_VERIFY` | `WANT_CHANNEL_ID_LOOKUP`, `PENDING_SESSION`, `PENDING_CERTIFICATE` | `Failed` (unexpected) |
| 4, 7, 8, 10, 13–19 and any other value | callback, async or connect modes the codec never enables | AWS-LC-only codes | `Failed` (unexpected) |

Treating unknown codes as fatal is not pedantry. In OpenSSL 3.0.0, an internal verification error made OpenSSL return the undocumented `SSL_ERROR_WANT_RETRY_VERIFY`, which "could result in crashes, infinite loops or other similar incorrect responses" in wrappers ([CVE-2021-4044](https://github.com/openssl/openssl/blob/master/CHANGES.md)).

### Ownership: one owner per C object, and C never outlives it (TB1–TB5)

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TB1** | Wrap each `SSL_CTX` and each `SSL` in a move-only Mojo owner whose destructor frees it exactly once. Attach the BIOs with `SSL_set0_rbio` and `SSL_set0_wbio` right after `SSL_new`, never with `SSL_set_bio`, whose seven reference rules the manual says to avoid. Hold the BIO pointers only as borrowed pointers: never `BIO_free` them, and take no `BIO_up_ref` ([SSL_set_bio(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_set_bio.pod); [SSL_free(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_free.pod)). An `Ssl` holds its `SslCtx` owner alive. | A LeakSanitizer run over 10,000 connect-and-close cycles reports no leak and no double free. A planted extra `BIO_free` turns ASan red. |
| **TB2** | Pass the owner itself to every FFI wrapper, never a pointer extracted beforehand (the repo's `AsFd` pattern from CLAUDE.md), and call `keep_alive` after every call that hands C a raw address. Strings are NUL-terminated, codec-owned copies, checked for embedded NULs first. Ciphertext and plaintext buffers outlive the call. | Regression tests modelled on `test_owner_outlives_syscall_when_last_use`, covering the `Ssl`, the BIOs, the SNI string, the ALPN list and the write buffer. They run under gate TG8, because a use-after-free inside libssl is invisible to plain ASan (measured). |
| **TB3** | Never mutate an `SslCtx` after its first `SSL_new`; a configuration change builds a new context ([openssl-threads(7)](https://github.com/openssl/openssl/blob/master/doc/man7/openssl-threads.pod)). | No setter exists on a built context (API review). |
| **TB4** | Mutate codec state only through `mut self` methods. Drivers never reassign fields of a local codec inside a loop, which is the trigger of Mojo 1.2.0's field-reassignment corruption bug in CLAUDE.md *(inference)*. | A review rule, plus ASan runs of every driver. |
| **TB5** | If the library is loaded with `dlopen`, keep the handle for the whole process and never `dlclose` it while a context exists, because OpenSSL 4 cleans up in a global destructor ([OpenSSL NEWS.md](https://github.com/openssl/openssl/blob/master/NEWS.md); [Mojo OwnedDLHandle](https://docs.modular.com/mojo/std/ffi/OwnedDLHandle)). | The handle is a process-lifetime global (review). |

### Result codes: clear the queue, classify everything, latch failures (TB6–TB8)

OpenSSL reports details through a per-thread error queue, and in 3.x `SSL_get_error` reads that queue: "The current thread's error queue must be empty before the TLS/SSL I/O operation is attempted, or SSL_get_error() will not work reliably" ([SSL_get_error(3), 3.5](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_get_error.pod)). AWS-LC checks the queue before anything else ([ssl_lib.cc](https://github.com/aws/aws-lc/blob/main/ssl/ssl_lib.cc)), and only OpenSSL 4.0 removed the dependency. The bug this causes is real. OpenWrt's TLS server failed healthy connections whenever another connection on the same thread had just failed, which Chrome triggers routinely ([openwrt-devel](https://desiato.infradead.org/pipermail/openwrt-devel/2020-March/027904.html)). Node left the queue dirty and got a CVSS 7.5 denial of service ([CVE-2023-23919](https://tenable.com/cve/CVE-2023-23919)).

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TB6** | Call `ERR_clear_error()` before every `SSL_do_handshake`, `SSL_read_ex`, `SSL_write_ex`, `SSL_shutdown` and `BIO_write_ex`. Call `SSL_get_error` immediately afterwards, on the same thread, with no other OpenSSL call and no user code in between. After a failure, drain the whole queue with an `ERR_get_error` loop into the error. The queue is empty whenever control returns to Mojo. | On one thread, connection A fails on a bad certificate, then connection B reaches `WANT_READ`, not `SSL_ERROR_SSL`. Test builds assert `ERR_peek_error() == 0` after every wrapper call, and a planted bug that skips the clear turns this red. |
| **TB7** | Classify every code as in the table above, with one constant table per library. Bound `WANT_WRITE` retries, and make every unknown value fatal. | A fault seam forces each `SSL_ERROR_*` value, including the "impossible" ones. Each ends in `Failed`, after which the seam counts zero further OpenSSL I/O calls and zero `SSL_shutdown` calls. |
| **TB8** | Latch `Failed`, `Truncated` and `PeerClosed`: afterwards every codec method returns the latched outcome without calling OpenSSL, as CPython's `got_eof_error` does. In OpenSSL 4, the call after an unexpected EOF fails with a generic error instead ([CPython _ssl.c](https://github.com/python/cpython/blob/main/Modules/_ssl.c)). | A read after `Truncated` returns `Truncated` with zero OpenSSL calls. |

### TLS 1.3 reads can write, so the codec reads until OpenSSL is empty (TB9–TB10)

After a TLS 1.3 handshake, the server sends session tickets (two by default) and either side may send a KeyUpdate. `SSL_read` processes these without returning any application data, and a requested KeyUpdate makes it queue a reply. A wrapper that stops after one empty read leaves ciphertext stranded in the read BIO. OpenSSL's issue 6234 in 2018 was exactly this, and the fix was to make `SSL_MODE_AUTO_RETRY` the default ([openssl#6234](https://github.com/openssl/openssl/issues/6234)); pyOpenSSL, Node and CPython still set it explicitly. A TCP read can also end anywhere inside a record, so split handling is the core of the codec, not an edge case.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TB9** | Set `SSL_MODE_AUTO_RETRY` explicitly (a no-op on AWS-LC). After every feed, loop `SSL_read_ex` until `WANT_READ`, `ZERO_RETURN` or a fatal code, even when the caller expects no data. Never use `SSL_pending` or `SSL_has_pending` as a signal that more input exists ([SSL_pending(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_pending.pod)). Drain the write BIO after every read. | After `openssl s_server`'s `K` command, a KeyUpdate reply appears in `poll_transmit` with no application data. `-num_tickets` 0, 2 and 8 give identical plaintext. |
| **TB10** | Produce identical events, and identical concatenated data, under any split of the input (contract 1, rule 4). | One shot, byte at a time, seeded random splits, and splits at record boundaries ±1 give the same results, across handshake, data, tickets, KeyUpdate and close_notify (gates TG4 and TG5). |

### Writes are copied once and retried byte for byte (TB11)

When `SSL_write` must be retried, "it must be repeated with the same arguments. The data that was passed might have been partially processed" ([SSL_write(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_write.pod)). A moved buffer fails with `SSL_R_BAD_WRITE_RETRY`, and AWS-LC says a failed write "still commits to the data passed in". Mojo makes the naive approach unsafe: a caller's span handed straight to `SSL_write_ex` is destroyed after its last use, so the retry would point into freed memory.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TB11** | Copy plaintext into a codec-owned queue, and call `SSL_write_ex` only after TC9, with at most 16 KiB per call. On `WANT_*`, retry with the same pointer and length, and never append to the buffer while a write on it is in flight. A zero-length write returns without calling OpenSSL. Set neither `SSL_MODE_ENABLE_PARTIAL_WRITE` nor `SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER`; OpenSSL 4.0.1 fixed a stale-buffer bug in exactly that mode's kTLS path ([CHANGES.md](https://github.com/openssl/openssl/blob/master/CHANGES.md)) *(not setting it is an inference)*. | A seam forces `WANT_READ` on the first write and records the retry's pointer and length, which are identical. Writes over 16 KiB and of 0 bytes behave. Plaintext queued before a failed verification never appears in transmit output. |

### A cut connection is Truncated, never a clean end (TB12–TB13)

**Truncation is an attack, not an accident.** A man in the middle can cut a connection between records, and a client that treats the cut like a clean close accepts half a response as the whole. Smyth and Pironti used this to break Helios voting and Microsoft and Google account flows ([USENIX WOOT '13](https://www.usenix.org/conference/woot13/workshop-program/presentation/smyth)). TLS marks a genuine end with a close_notify alert, which shows up as `SSL_ERROR_ZERO_RETURN`. Since OpenSSL 3.0, a TCP close without close_notify surfaces as `SSL_ERROR_SSL` with `SSL_R_UNEXPECTED_EOF_WHILE_READING` ([SSL_get_error(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_get_error.pod)).

`SSL_OP_IGNORE_UNEXPECTED_EOF` erases that distinction. nginx sets it and relies on HTTP framing instead ([nginx](https://github.com/nginx/nginx/blob/master/src/event/ngx_event_openssl.c)); CPython and curl do not set it. RFC 9112 settles what HTTP may accept: a response whose `Content-Length` was met, or whose terminating chunk arrived, is complete, while a response delimited by connection close is complete only if close_notify arrived ([RFC 9112 §9.8](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.8)).

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TB12** | Signal EOF only after every received byte has been fed. Afterwards, classify from the codec's own state, not from reason strings: `ZERO_RETURN` is `PeerClosed`, and any failure is `Truncated`. This works on OpenSSL 3, on OpenSSL 4's changed second call, and on AWS-LC, which ignores `BIO_eof` and may report `SYSCALL` with return 0 ([AWS-LC ssl.h](https://github.com/aws/aws-lc/blob/main/include/openssl/ssl.h)). Never set `SSL_OP_IGNORE_UNEXPECTED_EOF`. The HTTP client accepts `Truncated` only after a complete framed body, rejects close-delimited bodies, and never reuses the connection. | A FIN before the handshake, mid-handshake, after a record header only, mid-body, after a complete record without close_notify, and after close_notify each gives exactly `Truncated` or `PeerClosed`. At the HTTP level, a met `Content-Length` without close_notify is accepted, a short body is rejected, and a close-delimited body without close_notify is rejected. |
| **TB13** | On a healthy established connection, close with one `SSL_shutdown` and drain the write BIO, and never call `SSL_get_error` after a 0 return. Answer a peer's close_notify with one `SSL_shutdown`. Never call `SSL_shutdown` after `SSL` or `SYSCALL` errors, or during a handshake: just `SSL_free` ([SSL_shutdown(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_shutdown.pod)). | A seam counts `SSL_shutdown` calls on each path and finds 1, 1, 0 and 0. |

### Macros and widths differ between libraries, so bindings are generated per library (TB14–TB16)

Mojo's `external_call` binds C functions by symbol name, but nine of the calls this codec needs are not functions in OpenSSL 3. They are `#define` macros over `SSL_ctrl`, `SSL_CTX_ctrl` or `BIO_ctrl` with numeric command codes. In AWS-LC the same names are real functions, and the ctrl commands "will not work" ([AWS-LC PORTING.md](https://github.com/aws/aws-lc/blob/main/PORTING.md)). The types differ too. OpenSSL 3 takes options as `uint64_t`, while AWS-LC takes `uint32_t` options and a `uint16_t` version. A declaration with the wrong width compiles, runs and silently passes garbage.

| Rule | The wrapper must | A test or check must show |
|---|---|---|
| **TB14** | Keep one binding table per library and never mix them. On OpenSSL, call the macros through their entry points with constants extracted from the installed headers by a `gen_abi.py`-style tool: `SSL_ctrl` 55 (SNI, name type 0); `SSL_CTX_ctrl` 33 (mode) and 123 and 124 (minimum and maximum version); `BIO_ctrl` 130 (EOF return); and the groups-list and session-cache controls. Use the real `size_t BIO_ctrl_pending`, never the `int`-typed `BIO_pending` macro ([bio.h.in](https://github.com/openssl/openssl/blob/master/include/openssl/bio.h.in)). | CI regenerates the constants from the headers and fails on any drift, as `abi-check` does for the kernel. |
| **TB15** | Declare the option word as 64-bit on OpenSSL 3 and 32-bit on AWS-LC, the version argument as `uint16_t` on AWS-LC, and the `SSL_ERROR_*` constants per table. | After setting options, mode and version, reading them back gives exactly the values set. |
| **TB16** | Install no callback in the client codec, mirror no OpenSSL struct, and read only through accessor functions. | A grep finds no `abi("C")` function in `src/tls`'s client modules. |

### Memory is capped by the codec, because memory BIOs never refuse a write (TB17–TB18)

"Writes to memory BIOs will always succeed if memory is available: that is their size can grow indefinitely" ([BIO_s_mem(3)](https://github.com/openssl/openssl/blob/master/doc/man3/BIO_s_mem.pod)). A peer that floods ciphertext, or never reads, grows the heap until the codec stops it.

| Rule | The wrapper must | A test must show |
|---|---|---|
| **TB17** | Set `feed_capacity` to about one maximum record, roughly 17 KiB ([RFC 8446 §5.2](https://www.rfc-editor.org/rfc/rfc8446#section-5.2)), and pump to `WANT_READ` before the next feed; this also avoids the memory BIO's copy-on-every-write slowdown. Cap the transmit backlog, and stop calling `SSL_write_ex` beyond it. Cap the ciphertext fed before the handshake completes: for a client, above OpenSSL's 100 KiB peer-chain limit ([CVE-2023-2650 note](https://openssl-library.org/news/vulnerabilities/index.html#CVE-2023-2650)), for example 256 KiB; for a server, as in TS8 *(inference)*. Set `SSL_MODE_RELEASE_BUFFERS`, which saves about 34 KB per idle connection ([SSL_CTX_set_mode(3)](https://github.com/openssl/openssl/blob/master/doc/man3/SSL_CTX_set_mode.pod)), and never call `SSL_free_buffers`. | A peer streaming garbage, or an oversized chain, ends in `Failed` with resident memory bounded. A peer that never reads makes writes stop at the cap. |
| **TB18** | Cleanse codec-owned plaintext buffers with `OPENSSL_cleanse` before freeing them *(inference)*, and never register a keylog callback. | With `SSLKEYLOGFILE` set, no key log file appears. |

## The server profile stays small: ECDSA keys, no FFDHE, no tickets, one callback

A server faces anonymous strangers. They can open connections cheaply, make the server do expensive public-key work, hold buffers open and probe for any feature left on. Three risks dominate: exhausting the server's CPU and memory with handshakes, session-ticket keys that quietly undo forward secrecy, and callbacks that switch configuration mid-handshake. The repo's server model helps. With one thread and one edge-triggered epoll loop per process, every OpenSSL call runs on the loop thread and there is no cross-thread state. It also sidesteps the OpenSSL 3 lock contention that HAProxy measured at 27% of CPU ([HAProxy](https://www.haproxy.com/blog/state-of-ssl-stacks)).

**The certificate type decides handshake cost.** Measured on this host with `openssl speed` (OpenSSL 3.5.7, one core of a loaded 8-CPU machine):

| Operation | Per second |
|---|---|
| ECDSA P-256 sign | 41,287 |
| RSA-2048 sign | 2,740 |
| ML-KEM-768 encapsulate | 34,508 |

With an ECDSA certificate, a full TLS 1.3 handshake costs the server three or four cheap operations; with RSA-2048, the signature alone caps a core near 2,700 handshakes a second. Finite-field groups are a separate lever for attackers. OpenSSL 3.5's default group list still ends with `ffdhe2048:ffdhe3072` ([t1_lib.c](https://github.com/openssl/openssl/blob/openssl-3.5/ssl/t1_lib.c)), and the D(HE)at attack makes a server do expensive exponentiations while the client "needs very little CPU resources and network bandwidth" ([dheater](https://pypi.org/project/dheater/)).

**Default session tickets break the rules in this architecture.** OpenSSL generates its ticket key once per `SSL_CTX` and never rotates it ([ssl_lib.c](https://github.com/openssl/openssl/blob/openssl-3.5/ssl/ssl_lib.c)). With one context per SO_REUSEPORT worker, each worker has its own key, so a returning client resumes only about one time in N. And a worker that runs for weeks keeps a key that RFC 9325 says "MUST be changed regularly, e.g., once every week" ([RFC 9325](https://www.rfc-editor.org/rfc/rfc9325)). Anyone who obtains that key can decrypt every session it protected, forward secrecy notwithstanding ([SSL_CTX_set_tlsext_ticket_key_cb(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CTX_set_tlsext_ticket_key_cb.pod)). The obvious fix, `SSL_OP_NO_TICKET` on its own, switches TLS 1.3 to stateful tickets plus a server cache: the configuration behind CVE-2024-2511's unbounded memory growth ([advisory 2024-04-08](https://openssl-library.org/news/secadv/20240408.txt)).

**Callbacks are risky in two ways.** Switching contexts mid-handshake with `SSL_set_SSL_CTX` caused an out-of-bounds write, fixed on 2026-09-29 ([CVE-2026-72897](https://openssl-library.org/news/secadv/20260929.txt)). And a server that ignores ALPN can be confused with another protocol served under the same certificate. RFC 9325 counters that class (ALPACA) with a fatal `no_application_protocol` alert.

| Rule | The server must | A test must show |
|---|---|---|
| **TS1** | Use Mozilla intermediate: TLS 1.2 and 1.3 with the floor set explicitly, the six ECDHE AEAD suites for TLS 1.2 and the three TLS 1.3 suites, security level 2, `SSL_OP_NO_RENEGOTIATION`, and `max_early_data` left at 0. Never set `ALLOW_CLIENT_RENEGOTIATION`, `ALLOW_UNSAFE_LEGACY_RENEGOTIATION`, `ALLOW_NO_DHE_KEX` or `NO_EXTENDED_MASTER_SECRET`, and never clear `NO_COMPRESSION` ([Mozilla 6.0](https://ssl-config.mozilla.org/guidelines/6.0.json); [SSL_CTX_set_options(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CTX_set_options.pod)). | `sslyze --mozilla_config=intermediate` exits 0. tlsfuzzer's `test-renegotiation-disabled.py`, `test-hello-request-by-client.py` and `test-early-application-data.py` pass. |
| **TS2** | Set the groups to exactly `X25519MLKEM768:X25519:prime256v1:secp384r1`: no FFDHE, and no `DEFAULT` keyword. | testssl.sh `-f` and tlsfuzzer's `test-tls13-ffdhe-groups.py` show no FFDHE group accepted. |
| **TS3** | Load one ECDSA P-256 chain, plus an RSA-2048 chain only if old clients matter: the chain first, then the key, then `SSL_CTX_check_private_key` after each pair. Set `SSL_MODE_NO_AUTO_CHAIN`, as nginx does, so the chain sent is exactly the one configured. Fail startup on any error, on an expired leaf, or on a leaf that does not cover the configured names. Read the key from a file of mode 0600 or 0400, with no encrypted keys and no password callback ([SSL_CTX_use_certificate(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CTX_use_certificate.pod)). | A mismatched key, an expired certificate and a wrong-name certificate each stop startup with a clear error. |
| **TS4** | Do no resumption in v1: `SSL_CTX_set_num_tickets(ctx, 0)`, `SSL_OP_NO_TICKET` and `SSL_SESS_CACHE_OFF`, always all three together and never `NO_TICKET` alone. Any later ticket support uses keys that the supervisor generates and hands to workers over an inherited fd. Those keys rotate every 12–24 hours, with a session timeout below half the rotation period, and are held only in memory and zeroed on rotation. | tlsfuzzer's `test-tls13-count-tickets.py` expects 0 tickets, and a reconnect never resumes. |
| **TS5** | Install at most one callback: an ALPN selector, a static C-ABI Mojo function (`def(...) thin abi("C")`) built once at setup. It walks the client's list itself, accepts only an exact `http/1.1`, and points `out` into a static, process-lifetime buffer; otherwise it returns `SSL_TLSEXT_ERR_ALERT_FATAL`. It never raises, allocates or touches loop state ([SSL_CTX_set_alpn_select_cb(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CTX_set_alpn_select_cb.pod)). | tlsfuzzer's `test-alpn-negotiation.py` passes. A client offering only `h2` gets a fatal `no_application_protocol` alert. |
| **TS6** | Never call `SSL_set_SSL_CTX`. Check SNI after the handshake by comparing `SSL_get_servername` with the configured names, closing on a mismatch, and answer 421 when the HTTP `Host` differs from the SNI *(inference from RFC 9325's ALPACA discussion)*. Serve several names with one SAN certificate or with separate listeners. | An unknown SNI is closed before any request is processed. A `Host` that differs from the SNI gets 421. |
| **TS7** | Admit handshakes before OpenSSL sees a byte. Limit the handshakes started per worker per second, counted at accept as HAProxy's `maxsslrate` is, and cap concurrent handshakes separately from the connection cap. When either limit is hit, refuse before `SSL_new` ([HAProxy configuration.txt](https://github.com/haproxy/haproxy/blob/master/doc/configuration.txt)). | A burst over the cap is refused, and a seam counts no `SSL_new` for the refused connections. |
| **TS8** | Give every handshake one absolute deadline from accept, for example 10 seconds, that progress does not extend, as nginx and Go do ([nginx ngx_http_request.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_request.c); [Go server.go](https://github.com/golang/go/blob/master/src/net/http/server.go)). Cap the ciphertext accepted before the handshake ends at 32–64 KiB, rather than relying on OpenSSL's 131,396-byte ClientHello limit ([statem_srvr.c](https://github.com/openssl/openssl/blob/openssl-3.5/ssl/statem/statem_srvr.c)) *(the figures are inferences)*. | A Python peer dribbling a ClientHello one byte a second is closed at the deadline. 100 KiB of garbage before the handshake is closed at the cap. |
| **TS9** | After the handshake, feed at most one record before draining, and stop reading the socket while ciphertext is pending. Under edge-triggered epoll, call `SSL_read_ex` until `WANT_READ` before returning to the loop. Cap unsent ciphertext, and count the minimum rate in plaintext, not ciphertext. Close a peer whose reads consume input but yield no plaintext beyond a small budget per window: a KeyUpdate-flood guard that needs no per-message callback, where HAProxy has limited KeyUpdates to 100 a second since July 2026 ([HAProxy commit](https://github.com/haproxy/haproxy/commit/91004114fe)) *(the budget is an inference)*. | A KeyUpdate flood (tlsfuzzer's `test-tls13-keyupdate.py` with a high count, or a loop of `s_client` `k` commands) is closed. A non-reading client keeps memory bounded. A 10,000-connection run shows no leak. |
| **TS10** | On a graceful close, send one `SSL_shutdown`, flush, then run the existing linger logic. On a timeout, an error or abandoned output, send no close_notify. After a fatal error, flush the alert already in the write BIO, then close. Never call `SSL_shutdown` during a handshake. A graceful server shutdown lets in-flight handshakes finish under their deadline and sends close_notify on idle keep-alive connections ([nginx](https://github.com/nginx/nginx/blob/master/src/event/ngx_event_openssl.c)). | Seam counts per path, and the existing graceful-shutdown tests pass over TLS. |
| **TS11** | Log only the classified reason, the peer address, the SNI, and the version and cipher after success, with peer-caused failures at info level rather than as errors. Remove `SSLKEYLOGFILE` from every worker's environment, since a distribution libssl built with 3.5's `enable-sslkeylog` would write secrets there ([OpenSSL 3.5 CHANGES](https://github.com/openssl/openssl/blob/openssl-3.5/CHANGES.md)). | A worker started with `SSLKEYLOGFILE` set never creates the file. |
| **TS12** | Reload certificates on SIGHUP through the existing `SignalFd` path, or on a periodic check of inode, mtime and size. Build a new context with every startup check from TS3, and swap it in for new connections only; live connections keep the old one through OpenSSL's reference count ([SSL_new(3)](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_new.pod)). On any failure, keep serving with the old context. Raise an expiry alarm in the health output once less than a third of the lifetime remains. | A bad replacement file leaves the old certificate serving, and a good one reaches new connections without disturbing live ones. The alarm fires on a short-lived test certificate. |
| **TS13** | Build each worker's context after its re-exec, confine every `SSL` to the loop thread, and never use TLS across a fork without exec. | A workers test in the style of `tests/server/test_workers.mojo` passes over TLS. |
| **TS14** | Ship without kTLS, OCSP stapling, mTLS, in-process ACME or 0-RTT, for the reasons below. | `SSL_OP_ENABLE_KTLS` is never set, no status callback exists, and early data stays at 0 (option read-back). |

Four features are deferred, each for a reason that would have to change before it returns. **kTLS** needs OpenSSL to own the socket, because the kTLS control exists in the socket BIOs and not in the memory BIO ([bss_mem.c](https://github.com/openssl/openssl/blob/openssl-3.5/crypto/bio/bss_mem.c)). The kernel's TLS code has also had use-after-frees, one rated CVSS 7.1 ([CVE-2025-39682](https://starlabs.sg/advisories/25/25-39682/)), and receive-side rekeying arrived only in Linux 6.14, above the repo's 5.15 floor ([kernel TLS 6.14](https://docs.kernel.org/6.14/networking/tls.html)). HAProxy still marks kTLS experimental, and its gain is static-file throughput, not security.

**OCSP stapling** would need an outbound HTTP client, a callback, a cache and a refresh schedule inside the server. Meanwhile Let's Encrypt removed OCSP, and the Baseline Requirements now make OCSP a "MAY" ([CA/B Forum BRs](https://github.com/cabforum/servercert/blob/main/docs/BR.md)). Mozilla 6.0 still recommends stapling, a conflict this plan resolves against it. **mTLS** adds certificate parsing on the server, the code path of several 2026 CVEs, and Let's Encrypt stopped issuing client-authentication certificates in 2026, so internal mTLS needs a private CA anyway ([Let's Encrypt](https://letsencrypt.org/2025/05/14/ending-tls-client-authentication/)). **ACME** belongs in a sidecar that writes `fullchain.pem` and `privkey.pem` and signals the server. Let's Encrypt lifetimes shrink to 45 days by 2028 ([Let's Encrypt](https://letsencrypt.org/2025/12/02/from-90-to-45)), which is why TS12's expiry alarm matters.

**Fuzzing has to happen live, by splitting.** Mojo 1.2.0 offers no coverage instrumentation and no libFuzzer integration: `mojo build --help` lists only `--sanitize address|thread` (measured). Coverage-guided fuzzing of the Mojo side is therefore out of reach today. The practical substitute is seeded mutation of the byte streams between the codec and a real peer, in the repo's `MOJO_NET_SIM_SEED` replay style.

The notes suggested recording a transcript and replaying it. That cannot work for a handshake, because every new client sends a fresh random value and key share, so a recorded server reply no longer matches *(inference)*. The splitting and mutation must happen live: in T1, between the client codec and an `openssl` or Python peer, with the driver splitting what the codec receives at seeded points; after T2, between the client and server codecs in one process, which puts both directions under the seed. Mutations flip bits, duplicate, drop, truncate and inject alerts. The plaintext oracle is simple and strong: AEAD means any change must end in `Failed`, never in different data. The library's own parsers are fuzzed upstream by OSS-Fuzz and by tlspuffin, which has found 8 CVEs in TLS stacks ([tlspuffin](https://github.com/tlspuffin/tlspuffin/)).

**Sanitizers work, with one blind spot.** On this host, Mojo 1.2.0 programs were built with `--sanitize address` and linked to conda-forge's OpenSSL through `-Xlinker` flags, since `mojo build` rejects `-l` directly. They behaved as follows (measured):

| Case | ASan result |
|---|---|
| A double `SSL_free` | caught |
| Use-after-free in Mojo code or in libc's `memcpy` | caught |
| A context and connection never freed | caught by LeakSanitizer (35,584 bytes in 281 allocations) |
| A correct program | clean |
| `SSL_is_server` called on a freed `SSL` | **not caught**: the read happens inside uninstrumented libssl |

That blind spot is why TG8 exists. Valgrind from conda-forge could not start on this Debian host without `libc6-dbg`, and ASan on aarch64 was not tried.

### Supply chain and advisory tracking (TA1–TA8)

No vulnerability scanner reads `pixi.lock`: OSV-Scanner v2's formats do not include it ([Google Security Blog](https://security.googleblog.com/2025/03/announcing-osv-scanner-v2-vulnerability.html)). Nor do conda-forge packages carry Sigstore attestations yet ([prefix.dev](https://prefix.dev/blog/securing-the-conda-package-supply-chain-with-sigstore)). Tracking therefore has to be built. OpenSSL announces the date and severity of a release to the openssl-announce list one week ahead. It sends patches two weeks ahead only to OS vendors and qualifying projects, and only for Critical, High and Moderate issues ([OpenSSL security policy](https://openssl-library.org/policies/general/security-policy/)). A private, unpublished repo should assume it gets only the public notice *(inference)*.

### External review costs tens of thousands of dollars and should stay narrow

OSTIF puts initial audits at $30,000–$200,000, with costs tied to "complexity, labor hours, and type of audit". Its AWS-funded program averaged $74,000 an audit in 2022–2023 ([OSTIF](https://ostif.org/get-an-audit/)). For scale, curl's audit took four consultants about six engineer-weeks ([OSTIF impact report](https://ostif.org/wp-content/uploads/2023/02/Security-Audit-Impact-Report-OpenSSF-Google.pdf)), and Cure53 spent 30 person-days on rustls, ring and webpki ([rustls audit](https://jbp.io/2020/06/14/rustls-audit/)).

A narrow scope fits this repo: the `tls` wrapper, its verification configuration, each consumer's TLS policy (HTTP pool keys, `SSLRequest` and `sslmode`, `rediss://`) and a threat model. By analogy with curl, that is plausibly a 1–3 engineer-week engagement *(inference, not a quote)*. The notes name Trail of Bits, NCC Group, Cure53 and X41 as firms to approach; none advertises a "TLS integration review" product. Funding programmes such as OSTIF and the Sovereign Tech Agency target open-source projects, so a private repo without a licence is likely ineligible *(inference)*.

The order matters more than the dates. T0 answers the questions that would otherwise surface as rework: how Mojo loads libssl in each mode, and which trust store each mode finds. T1 lands every verification rule before any consumer can depend on a looser version. H8 is the critical path to hosted model APIs, and P9 and R8 can run beside it. The review gate sits before the server, because the server adds the largest attack surface, exposed to strangers, and because the bugs found in other projects' TLS glue are exactly what a review of the wrapper targets. From T1 to S7, the total comes to about 8–12 person-weeks, plus T0 and the review. Given how fast the repo's earlier milestones landed, read these figures as relative sizes, not a schedule.

## Ten decisions remain open, and some risk stays whatever is decided

| Decision | Options | Recommendation and why |
|---|---|---|
| **TD1: OpenSSL line and pin** (urgent) | 3.5 LTS; stay on 3.6; 4.x; AWS-LC | Pin `openssl >=3.5.9,<4` now, and the environment to `3.5.*` before 2026-11-01, when 3.6's fixes stop. 4.x conflicts with conda-forge's Python today. Plan a T4 move to 4.2 LTS after April 2027, once conda-forge migrates. |
| **TD2: Loading mechanism** | Link-time `external_call` with `-Xlinker` link flags (measured to work with `mojo build`); runtime `dlopen` through `OwnedDLHandle` | Decide in T0, by measurement. Choose the mechanism that works under `mojo run`, `mojo build` and the installed package on both architectures, loads a libssl whose version and `OPENSSLDIR` the wrapper can check and log, and fails closed at start when a symbol is missing. `dlopen` gives the last natively; link-time binding fails at load *(inference)*. |
| **TD3: Wording of the FFI exception** | libssl reads CA bundles and keys itself; or `linux.fs` reads them and passes bytes through memory BIOs | Let libssl read files at context build, and record in `docs/design.md` that its memory, randomness and build-time file syscalls are inside the exception, and sockets never are. Passing bytes keeps the "every syscall in inline asm" wording literally true for files, but adds X.509 and PEM object lifetimes to the FFI surface *(inference)*. |
| **TD4: PostgreSQL `sslmode=require`** | Enforce `verify-full`; reject `require` | Enforce `verify-full`, documented as a deliberate departure from libpq: hosted connection strings say `require`, and the departure fails closed. Refuse `allow` and `prefer` either way. |
| **TD5: Strictness that can break old private CAs** | Keep CN fallback, partial wildcards and partial chains off; or offer switches | Keep them off, with no switch. Public CAs always include SANs, and the fix for an old private certificate is reissuing it, not a knob that weakens every connection. |
| **TD6: Session resumption** | None; a keyed cache | None in v1, on client and server. Pooled keep-alive connections make the saving small, and resumption is where curl's reuse CVEs lived. |
| **TD7: Server profile** | Mozilla intermediate (TLS 1.2 and 1.3); modern (TLS 1.3 only) | Intermediate by default, modern as a configuration. TLS 1.3-only removes TLS 1.2's ticket and renegotiation paths, but it drops older clients. |
| **TD8: When AWS-LC becomes a backend** | Now; when conda-forge carries its LTS; never | Shape `tls.ffi` for a second table now, and implement T3 only once conda-forge ships AWS-LC's 4.x LTS with a record of timely security releases. |
| **TD9: External review** | None; a narrow integration review; a full audit | A narrow review after T1, H8, P9 and R8, before S7 is enabled by default or published. It is inferred at 1–3 engineer-weeks, against a published range of $30,000–$200,000 for whole projects. Licensing and publication affect eligibility for funding. |
| **TD10: Revocation** | None online, stated; OCSP or CRL fetching | Accept no online revocation and say so in the documentation. Add an opt-in, hard-fail CRL-file mode only for a named private-PKI user. |

**What stays risky, in plain words.** The library itself will have new bugs, most likely in how it parses a hostile server's certificate, the one job no configuration removes. When OpenSSL publishes a fix, users stay exposed for the embargo, plus conda-forge's 0–5 days, plus however long the repo takes to release. A bug an attacker finds first has no such window at all. The tests find only what someone thought to test: fifteen gates and 71 rules cover every failure class the research found, and an attacker needs only one class nobody listed. The external review is the only check on the tests' imagination, and its value ages as the code changes.

Several weaker spots remain by design or by circumstance. Nothing checks for revoked certificates, so a server whose key was stolen and whose certificate was withdrawn stays trusted until the certificate expires: up to 200 days today, 47 days from 2029. Validation trusts the system clock, so a wrong clock accepts expired certificates or rejects valid ones. The root store is only as fresh as the lock file, so a CA that browsers distrust stays trusted here until the next update and release. Timing leaks and other side channels inside OpenSSL are inherited, out of the wrapper's reach.

The Mojo compiler is young. CLAUDE.md already records miscompilations and early destruction in Mojo 1.2.0, and a compiler bug can turn correct-looking wrapper code into a use-after-free; ASan and the lifetime regression tests reduce that risk without removing it. Users can still choose badly, for example a custom CA bundle that trusts too much, and the API can make such choices explicit but cannot make them for the user. On the server side, the private key lives in process memory, an attacker with enough machines can still exhaust handshake capacity, and SNI reveals the server name to anyone watching the network.

## Conclusion

The research moves the effort away from where instinct puts it. The instinct is to pick the most secure library and trust it. The evidence says packaging and patch speed settle the library choice, and that the exploitable mistakes sit in the few hundred lines that connect the library to its caller. Those lines fail in one characteristic way: OpenSSL reports success after a check did not run, so code that looks correct, and passes every "does it connect" test, can still accept an attacker. That makes the problem tractable for a maintainer who cannot audit TLS. A wrong host, a missing certificate, a cut connection and a stale error are each a scenario a test can create on demand. The rule set is long because each rule names one such scenario, not because TLS needs expert judgement at every step.

The plan promises something narrower than "no vulnerabilities", and more useful. Every failure class seen in two decades of integration CVEs gets a test, every test gets a planted bug that proves it can fail, and every new library advisory reaches users within days. Unlike the promise of no vulnerabilities, these commitments can be checked. The open question is no longer whether to trust OpenSSL, but whether the project keeps the gates honest as the code grows: rerunning the planted bugs, triaging each advisory, and repeating the external review when the server ships. That maintenance, more than the initial build, is what keeps "no exploitable mistakes" true over time.
